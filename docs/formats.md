# 檔案格式

分析對象：`新改曹操傳6.6修正版`（社群 MOD，以下簡稱 6.6）。全部 1246 個檔、1.5 GB。
文字編碼一律是 **GBK**（簡繁混用，例如「遊戲指南」「曹操」）。

## 目錄總覽

| 路徑 | 數量 | 內容 |
|---|---|---|
| `Ekd5.exe` | 1 | 主程式（1.1 MB，MOD 改過的引擎） |
| `*.e5`、`E5/*.e5` | 9 + 40 | 資料封包，多數是 LS12 格式（見下） |
| `RS/R_*.eex` | 126 | 劇情腳本（城內、對話） |
| `RS/S_*.eex` | 123 | 戰場腳本（每關一個） |
| `MAP/m*.jpg` | 125 | 戰場大地圖，標準 JPEG |
| `SoundTrk/*.mp3` | 199 | BGM |
| `WAV/*.wav` | 145 | 音效 |
| `*.avi` | 4 | 開場、片尾動畫 |
| `SV/SV.E5S` | 1 | 存檔 |
| `System.ini` | 1 | MOD 工具用的位址設定（exe 內資料表的偏移，逆向 exe 時可參考） |
| `修改器與修改記錄/` | — | 社群編輯器和修改記錄，不是遊戲本體 |

## LS12 封包（`tools/ls12.py`）

```
0x000  16 bytes   magic "Ls12" + 空白或 \0
0x010  256 bytes  字典
0x110  目錄，每項 12 bytes big-endian：壓縮後大小, 原始大小, 偏移
       目錄一直延伸到第一筆資料的偏移（不一定以全 0 結尾）
```

- 壓縮後大小 == 原始大小：資料未壓縮，直接存放。6.6 的大多數封包都是這種情況。
- 不一樣大時就是 LZ 壓縮 bitstream（MSB first）。讀取規則：
  - 一串 1 以 0 結束，總長 n bits，再讀 n bits，code = 2^n − 2 + 後面那 n bits。
  - code < 256：輸出 `dict[code]`。
  - 否則：往回距離 = code − 256，長度 = 下一個 code + 3，從已輸出的資料往回複製。
- 驗證方式：DT、Meff、Pmap、Weather 裡的壓縮項目解壓後，檔頭跟同封包裡未壓縮項目的結構一致。

### Data.e5

| 項 | 大小 | 內容 |
|---|---|---|
| 0 | 32768 | 武將，32 bytes × 1024。0–15：名稱（GBK，\0 結尾），16–31：數值（待解） |
| 1 | 2600 | 道具，25 bytes × 104。0–14：名稱，15–24：數值（待解） |
| 2 | 4608 | 待查 |
| 3 | 2800 | 待查（像兵種相剋或地形表） |
| 4 | 2400 | 待查（值多為 0x50–0x78，像地形移動或命中修正百分比） |
| 5 | 15520 | 策略（第一筆是「灼热」），每筆大小待確認 |
| 6–9 | — | MOD 保留的空白區段（「闲置区段」） |

| 檔案 | 內容 |
|---|---|
| `Imsg.e5` | 說明文字（策略、道具說明），GBK 字串直接串接 |
| `Star.e5` | 寶物名稱和數值，每筆是 GBK 名稱 + `\r\n` + 數值 |

| `E5/Mcall00–22.e5` | 召喚／特殊動畫。檔頭有格數與寬高（例：300 × 300），後面接 frame 資料 |
| `E5/Mark.e5` | 調色盤或標記用色表（RGB 三元組重複出現） |
| `Mark.DEC` | 標記名稱表（GBK） |

## EEX 腳本（`RS/*.eex`）

```
0x00  "EEX\0"
0x04  01 02 00 00 00 00   版本？
0x0a  u32  區段（scene）數
0x0e  ...  指令流：u16 opcode + 參數，字串是 GBK 並以 \0 結尾
```

- `R_000.eex` 的開頭是遊戲指南文字；`S_000.eex` 開頭是「HEX我军设定」「个人装备设定」這類區段標題。
- opcode 表還沒整理，這是第 2 階段的重點。社群的「剧本编辑器v0.24」（`修改器與修改記錄/`）可以拿來交叉比對 opcode 的意思。
