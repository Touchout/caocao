# 檔案格式

分析對象：`新改曹操傳6.6修正版`（社群 MOD，以下簡稱 6.6）。全部 1246 個檔、1.5 GB。
文字編碼一律是 **GBK**（簡繁混用，例如「遊戲指南」「曹操」）。

## LS12 封包（`tools/ls12.py`）

```
0x000  16 bytes   magic "Ls12" + 空白或 \0
0x010  256 bytes  字典
0x110  目錄，每項 12 bytes big-endian：壓縮後大小, 原始大小, 偏移
       目錄一直延伸到第一筆資料的偏移（不一定以全 0 結尾）
```

- 壓縮後大小 == 原始大小：資料未壓縮，直接存放。6.6 的大多數封包都是這種情況。
- 不一樣大時就是 LZ 壓縮 bitstream（MSB first）。讀取規則：
  - 一串 1 以 0 結束，總長 n bits，再讀 n bits，code = 2^n − 2 + 後面那 n bits。
  - code < 256：輸出 `dict[code]`。
  - 否則：往回距離 = code − 256，長度 = 下一個 code + 3，從已輸出的資料往回複製。
- 驗證方式：DT、Meff、Pmap、Weather 裡的壓縮項目解壓後，檔頭跟同封包裡未壓縮項目的結構一致。

## Hexzmap（`tools/hexzmap.py`）

- 每筆：u8 寬、u8 高（單位 16 px），格數 = 值 ÷ 3；後面每格 1 byte 地形編號，逐列排列。
- 第 N 筆對應 `MAP/mNNN.jpg`，一格 48 × 48 px。126 筆的大小都跟地圖 JPEG 尺寸吻合。
- 戰場用哪張地圖由劇本的 0x27 背景显示決定：背景模式（型別 0x2D）= 3 時，型別 0x15 的值 + 變數4051×100 就是地圖編號
  （exe：0x413D13 寫入全域 0x510CFE，0x463D4F 組出 `MAP\M%03d.Jpg`）。
- 地形名稱表在 `Ekd5.exe` 檔案偏移 0x8AE70（GBK，\0 分隔），編號 0–33：
  平原、草原、树林、荒地、山地、岩山、山崖、雪原、桥梁、浅滩、沼泽、池塘、小河、大河、栅栏、城墙、城内、城门、城池、关隘、
  鹿砦、村庄、兵营、民居、宝物库、水池、火、船、祭坛、地下、地雷、战壕、掩体、工事。
- 驗證：`--overlay` 把地形名稱疊到大地圖上，山崖、城牆、城門、兵營都落在畫面對應位置。

## EEX 腳本（`tools/eex.py`）

249 個正式劇本（`R_*` 126 個、`S_*` 123 個）全部能完整解析，每個區塊長度都剛好對上。
`RS/` 裡另外兩個 MOD 作者的草稿檔（`單挑.eex`、`記錄寫法---.eex`）格式不完整，不在遊戲流程裡。

### 檔案結構

```
0x00  "EEX\0"
0x04  01 02 00 00 00 00
0x0A  u32 scene 偏移[]          第一個偏移 = 表的結尾，所以 scene 數 = (第一個偏移 − 0x0A) / 4
scene   = u16 section 數 + section*
section = u16 長度 + 內容
```

### 指令

- 指令 = u16 opcode + 參數*，opcode 範圍 0x00–0x7B（名稱見 `tools/eex_opcodes.txt`，取自社群劇本編輯器）。
- 參數 = u16 型別碼 + 值：型別 4 → i32，型別 5 → GBK 字串（\0 結尾），其他型別 → u16。
  型別 2、0x38、0x39 的值 ≥ 0xEFFF 時代表變數（引擎從 0x502000 的變數表取值）。
- 每個 opcode 讀哪些參數由引擎的處理函式決定，檔案裡沒有記錄。參數型別表在 `tools/eex_signatures.json`。
  其中只有 0x05 变量测试會隨資料變動：兩組（要成立／要不成立）各是 (0x35, 數量 N) 加上 N 個原始 u16 變數編號。
- 區塊：
  - opcode 0 在區塊結尾 = 區塊結束；不在結尾時後面接 u16 長度 + 子區塊（前面的條件指令都成立才執行）。
  - section 內容 = 内部信息（名稱）+ 條件指令* + 0 + 長度 + 本體，本體延伸到 section 結尾。
  - opcode 1 子事件 = 一個指令（内部信息名稱或條件測試）+ u16 長度 + 子區塊。
  - 0x76 无条件跳转會直接改串流位置。

### 引擎內部（`Ekd5.exe`，6.6 版）

| 位址（VA） | 內容 |
|---|---|
| 0x4109E6 | 指令分派：讀 opcode，> 0x7B 是錯誤；0、1 直接回傳狀態碼給上層；其餘查跳轉表 |
| 0x410A38 | 跳轉表，索引 = opcode − 2，共 122 項 |
| 0x4183F7 | `read_param(type)`（thiscall）：讀 u16 型別碼並跟期望型別比對，不符就回傳 0x8000 / 0x80000000 |

### 解析方式

`tools/re/eexemu.py` 用 Unicorn 把 exe 的 opcode 處理函式真的跑起來：讀參數用 exe 原本的程式碼，遊戲狀態全部當 0，
Windows API 直接回傳 0，除以零當 0。然後記錄它讀了哪些型別、串流指標前進多少。
同一個 opcode 量 3 次，型別序列都一樣後就改成直接解碼（每個參數都帶型別碼，可順便驗證）。
`tools/re/scan_handlers.py` 是早期的靜態掃描版本，只抓得到一部分，留作參考。

輸出：`python3 tools/eex.py <Ekd5.exe> -o out/eex RS/*.eex`，每個劇本一個 `.txt`。
